# 业务认证鉴权设计总览

## 1. 总体目标

本业务不自己维护登录密码，也不让调用方在请求里自报身份。

核心原则是：

- Keycloak 负责用户登录、Token 签发和基础角色。
- FastAPI 后端负责业务权限、账号启停、任务归属和 API Key 管理。
- 用户身份统一使用 Keycloak Token 中稳定的 `sub`。
- 长效 API Key 仍然基于 Keycloak Offline Token，不是后端自造的一套独立密钥体系。

## 2. Keycloak 中的关键设置

Keycloak 侧主要有四类 Client。

| Client | 类型 | 作用 |
| --- | --- | --- |
| `trade-access-api` | Resource Client | 表示被保护的后端 API，定义基础角色和 Token audience |
| `trade-access-portal` | Public Client | 普通用户浏览器登录 |
| `trade-access-admin-portal` | Public Client | 管理员浏览器登录 |
| `trade-access-offline` | Confidential Client | 普通用户创建长期 `sk-` API Key |

`trade-access-api` 下有两个基础角色：

- `trade-access-user`：允许进入普通业务 API。
- `trade-access-admin`：允许进入管理员 API 的基础门槛。

Portal 和 Offline Client 都需要让签发出的 Access Token 带上：

```text
aud = trade-access-api
resource_access.trade-access-api.roles
```

后端只读取这些标准 Token 字段，不把 IP、端口、业务动作写进 Keycloak Token。

## 3. 后端如何验证 Keycloak Token

请求进入 FastAPI 后，后端会校验 Bearer Token：

```text
Authorization: Bearer <keycloak_access_token>
```

校验重点：

- RS256 签名。
- `iss` 是否是指定 Realm。
- `aud` 是否包含 `trade-access-api`。
- `exp`、`iat`、`sub` 是否有效。
- `resource_access.trade-access-api.roles` 是否包含所需基础角色。

校验通过后，后端生成一个内部 `Principal`，核心字段是：

```text
subject_id = Keycloak sub
subject    = preferred_username 或 sub
roles      = Keycloak Client Role
permissions = 本地数据库中的业务权限
```

也就是说，Keycloak 解决“你是谁”，后端解决“你在这个业务里能做什么”。

## 4. 本地业务权限模型

后端用 SQLite 保存业务授权，主键是 Keycloak User 的 `sub`。

本地保存的内容主要是：

- 用户 Profile：`user` 或 `admin`。
- 是否启用：`enabled`。
- 业务权限：例如 `firewall.ip.allow`、`firewall.ports.allow`、`firewall.job.read`。
- API Key 元数据：名称、哈希、创建时间、最后使用时间、吊销状态。

当前业务不再按“管理员分配 IP 白名单”限制用户。用户提交的目标 IP 只要求是合法 IPv4 单地址，`mask` 固定为 `32`。

## 5. 管理员授权流程

管理员登录后端管理入口时，必须同时满足：

- Token 来自 `trade-access-admin-portal`。
- Keycloak Role 包含 `trade-access-admin`。
- 本地权限包含 `identity.user.manage`。
- 本地账号未禁用。

管理员保存用户授权时，后端会做两件事：

1. 通过 Keycloak Admin API 给该用户设置 `trade-access-user` 或 `trade-access-admin` 角色。
2. 在本地数据库按用户 `sub` 保存 Profile、启停状态和业务权限。

这里使用一个后端专用的 Keycloak Provisioning Client。它只保存在服务端，用 Client Credentials 调 Keycloak Admin API。

## 6. 普通用户调用流程

普通用户有两种调用方式。

第一种是短期 Access Token：

```text
用户登录 Keycloak
-> 浏览器获得 Access Token
-> 请求后端 API
-> 后端验 Token
-> 按 sub 读取本地权限
-> 执行业务权限判断
```

第二种是长期 API Key：

```text
Authorization: Bearer sk-<keycloak_offline_token>
```

长期 API Key 的本质不是后端随机生成的密码，而是 Keycloak Offline Token 加上固定前缀 `sk-`。

长期 API Key 只面向普通用户，管理员账号不创建个人 `sk-`。

## 7. 长期 sk- API Key 如何实现

用户创建 API Key 时，流程是：

```text
当前用户已登录
-> 后端为该用户发起 trade-access-offline 授权流程
-> Keycloak 返回 offline token
-> 后端生成 sk-<offline_token>
-> 只把完整 key 展示一次
-> 数据库只保存 key 的 SHA-256 哈希和元数据
```

后续调用时：

```text
收到 sk-<offline_token>
-> 后端先按哈希查本地记录，确认未吊销
-> 用 offline token 向 Keycloak 换短期 Access Token
-> 验证 Access Token 的签名、aud、iss、sub
-> 确认换回来的 sub 和本地 key 绑定的 subject_id 一致
-> 按 sub 读取最新本地业务权限
```

因此，即使用户保存的是长期 `sk-`，身份来源仍然是 Keycloak。

## 8. 为什么不把权限放进 Token

业务权限不放进 Keycloak Token，主要是为了让权限变更立即生效。

例如管理员停用用户、删除 API Key、调整接口权限后，后端下一次请求会重新读取本地数据库。

这样可以避免：

- Token 生命周期内权限旧值继续生效。
- 每次业务权限变更都要修改 Keycloak Token Mapper。
- 把端口、IP、业务动作等动态信息塞进身份系统。

## 9. 当前安全边界

需要重点记住：

- Access Token 和 `sk-` 都是 Bearer 凭据，泄露后就可以被重放。
- 生产环境必须使用 HTTPS。
- `trade-access-offline` 的 `client_secret` 只保存在后端。
- 完整 `sk-` 只在创建成功时展示一次。
- 删除 API Key 后，本地哈希记录被吊销，后端立即拒绝该 key。
- 在本地禁用用户后，浏览器 Token 和长期 `sk-` 都不能继续通过本地业务授权。

## 10. 一句话总结

Keycloak 是身份和 Token 的权威来源；FastAPI 用 Keycloak `sub` 作为稳定用户身份，在本地做业务授权和 API Key 管理；长期 `sk-` 只是 Keycloak Offline Token 的调用形式，不是脱离 Keycloak 的自定义密钥体系。
