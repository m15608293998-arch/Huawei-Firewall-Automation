# Trade Access API 首次生产环境部署全流程

> **版本提示（2026-06-09）：** 本文档中的 `X-API-Key` 部署步骤属于旧版方案，当前
> API 已改为管理员 Keycloak PKCE 登录和普通用户应用 SK。生产部署认证部分请以
> `docs/Keycloak标准认证鉴权实施说明.md` 为准；Ansible、Worker、SSH 和系统服务部分仍可参考。

本文档用于首次将 Trade Access API 部署到生产环境，覆盖：

- API 节点准备
- Python、Ansible 与项目依赖安装
- 防火墙 SSH 配置
- Keycloak Realm、Client、角色与 Service Account 配置
- Provisioning Client 配置
- 初始管理员引导
- SQLite、Runner artifacts 持久化
- systemd 与 HTTPS 配置
- 管理员 UI 首次使用
- 验收、备份、恢复和密钥轮换

本文档以以下示例环境为基础，部署时请替换实际地址和名称：

| 项目 | 示例值 |
|---|---|
| Keycloak 地址 | `https://keycloak.example.internal` |
| Keycloak Realm | `trade-access` |
| API 域名 | `https://trade-access.example.internal` |
| API 节点 | `192.168.6.38` |
| 防火墙管理地址 | `<FIREWALL_MGMT_IP>` |
| 服务运行用户 | `ansiblerun` |
| 项目目录 | `/opt/trade-access` |
| 持久化目录 | `/var/lib/trade-access` |
| 配置目录 | `/etc/trade-access` |

> 生产环境不要将项目、数据库或 Runner artifacts 长期放在 `/tmp` 下。

## 1. 部署架构

```text
用户/管理员浏览器或调用程序
  -> HTTPS
  -> Nginx/企业反向代理
  -> FastAPI :8000
  -> Keycloak认证和角色验证
  -> SQLite权限表和任务队列
  -> Worker
  -> ansible-runner
  -> SSH
  -> Huawei USG6000E
```

API和Worker当前由同一个启动脚本统一拉起：

```bash
python3.12 scripts/run_services.py
```

FastAPI负责接收请求和写入持久化队列，Worker按顺序执行防火墙任务。

## 2. Keycloak Client 职责

生产环境至少需要以下三个初始 Client：

### 2.1 `trade-access-api`

资源 Client，负责承载以下 Keycloak Client Role：

```text
trade-access-user
trade-access-admin
```

API验证Access Token中的：

```text
aud = trade-access-api
resource_access.trade-access-api.roles
```

### 2.2 `trade-access-provisioner`

仅供FastAPI后端使用，通过Keycloak Admin REST API自动完成：

- 创建调用方Client
- 启用Service Account
- 分配普通用户或管理员角色
- 配置角色作用域
- 获取或轮换Client Secret
- 启用或停用Client

其Secret只能保存在API服务器，禁止提供给前端用户或普通管理员。

### 2.3 `trade-access-admin-client`

首次部署时的管理员调用方Client，用于生成管理员`X-API-Key`并登录：

```text
/admin-ui
```

完成首次引导后，管理员可通过Admin UI创建其他普通用户或管理员Client。

## 5. 配置防火墙 SSH

### 5.1 创建或导入SSH私钥

```bash
sudo -u ansiblerun mkdir -p /home/ansiblerun/.ssh
sudo chmod 700 /home/ansiblerun/.ssh
```

如果需要新建密钥：

```bash
sudo -u ansiblerun ssh-keygen \
  -t rsa \
  -b 2048 \
  -f /home/ansiblerun/.ssh/usg6000e_trade_access \
  -C trade-access-production
```

设置权限：

```bash
sudo chmod 600 /home/ansiblerun/.ssh/usg6000e_trade_access
sudo chmod 644 /home/ansiblerun/.ssh/usg6000e_trade_access.pub
```

由防火墙管理员将公钥绑定到专用SSH用户。

### 5.2 修改防火墙固定配置

编辑：

```text
/opt/trade-access/group_vars/all.yml
```

同一个文件末尾已经包含完全注释的生产配置区块。先备份测试配置：

```bash
sudo -u ansiblerun cp \
  /opt/trade-access/group_vars/all.yml \
  /opt/trade-access/group_vars/all.yml.test-backup
```

编辑 `all.yml`，删除或注释当前 TEST-FW 配置，将
`BEGIN_PRODUCTION_CONFIG` 和 `END_PRODUCTION_CONFIG` 之间的内容整体取消注释，
然后由网络管理员确认：

- `trade_access_api.firewall_targets` 依次为 `PG-FW`、`PG-FW-1`、`IDC-FW`
- `firewall_parallel_workers` 是 `3`，`firewall_child_max_attempts` 是 `2`
- `PG-FW`：IP 使用 `public/private/Internet`，Application 使用 `private`
- `PG-FW-1`：IP 和 Application 都使用 `public`
- `IDC-FW`：IP 使用 `private/Internet`，Application 使用 `private`
- 每个配置档均有正确的管理 IP、SSH 账号和认证信息
- 各空间的 `address_set_name` 是实际生产 Address Set 名称
- `name_prefix` 是 `UD_TServe_`
- `name_prefix` 必须以华为设备要求的 `UD_` 开头
- `application_group_name` 是 `UDG_TradeServers`
- `rule_port_limit` 是 `4`
- `application_rule_limit` 是 `8`
- `commit_security_engine`
- `save_config`

三台设备的 `device_host`、`device_user`、`device_password` 直接填写在各自
profile 中，不使用环境变量引用。该文件包含生产密码，必须限制权限、纳入受控
备份并禁止提交到 Git；所有配置由网络管理员审核后再上线。

### 5.3 手工验证SSH

下面的连接检查对 `PG-FW`、`PG-FW-1`、`IDC-FW` 三个管理地址分别执行：

```bash
sudo -u ansiblerun ssh -tt \
  -i /home/ansiblerun/.ssh/usg6000e_trade_access \
  -o PreferredAuthentications=publickey \
  -o PasswordAuthentication=no \

  -o HostkeyAlgorithms=+ssh-rsa \
  -o StrictHostKeyChecking=no \
  -o UserKnownHostsFile=/dev/null \
  trade_access_api@<FIREWALL_MGMT_IP>
```

看到防火墙命令提示符后退出：

```text
quit
```

### 5.4 Playbook语法检查

```bash
cd /opt/trade-access
sudo -u ansiblerun /opt/trade-access/.venv/bin/ansible-playbook \
  --syntax-check playbooks/trade_server_access.yml
```

## 6. Keycloak 初始化

以下操作均在生产Keycloak中完成。

### 6.1 创建或确认Realm

登录Keycloak管理控制台：

```text
https://keycloak.example.internal/admin/
```

创建或选择Realm：

```text
trade-access
```

不要把业务Client创建在`master` Realm。

### 6.2 创建资源Client `trade-access-api`

进入：

```text
Clients -> Create client
```

填写：

```text
Client type: OpenID Connect
Client ID: trade-access-api
```

该Client作为API资源和角色命名空间使用，不需要通过它登录用户。建议关闭：

```text
Standard flow
Direct access grants
Implicit flow
Service accounts roles
```

保存后进入：

```text
Clients -> trade-access-api -> Roles
```

创建两个Client Role：

```text
trade-access-user
trade-access-admin
```

### 6.3 确认默认`roles` Client Scope

进入Realm的：

```text
Client scopes -> roles
```

确认其中存在用于Access Token的Client Role映射和Audience Resolve映射。

后续调用方Token必须包含：

```json
{
  "aud": ["trade-access-api"],
  "resource_access": {
    "trade-access-api": {
      "roles": ["trade-access-user"]
    }
  }
}
```

### 6.4 创建Provisioning Client

进入：

```text
Clients -> Create client
```

填写：

```text
Client type: OpenID Connect
Client ID: trade-access-provisioner
```

能力配置：

```text
Client authentication: ON
Authorization: OFF
Standard flow: OFF
Direct access grants: OFF
Implicit flow: OFF
Service accounts roles: ON
```

保存后进入：

```text
Clients -> trade-access-provisioner -> Service account roles
```

点击`Assign role`，选择`Filter by clients`，从`realm-management`分配：

```text
manage-clients
query-clients
manage-users
query-users
```

不要直接分配`realm-admin`。

进入：

```text
Clients -> trade-access-provisioner -> Credentials
```

复制Client Secret。该Secret只能写入API服务器的受限配置文件。

### 6.5 创建初始管理员Client

创建：

```text
Client ID: trade-access-admin-client
Client type: OpenID Connect
Client authentication: ON
Standard flow: OFF
Direct access grants: OFF
Implicit flow: OFF
Service accounts roles: ON
```

保存后进入：

```text
Clients -> trade-access-admin-client -> Service account roles
```

选择`Filter by clients`，从`trade-access-api`分配：

```text
trade-access-admin
```

然后进入：

```text
Clients -> trade-access-admin-client -> Client scopes
-> trade-access-admin-client-dedicated
-> Scope
```

配置：

```text
Full scope allowed: OFF
```

将`trade-access-api`下的`trade-access-admin`加入Role scope mappings。

最后进入`Credentials`复制该Client Secret。

> `trade-access-provisioner`的Secret用于API后端管理Keycloak；
> `trade-access-admin-client`的Secret用于生成管理员X-API-Key。两者不能混用。

### 6.6 验证初始管理员Token

在安全终端执行：

```bash
read -rsp "管理员 Client Secret: " ADMIN_CLIENT_SECRET
echo

TOKEN_RESPONSE=$(curl -fsS -X POST \
  'https://keycloak.example.internal/realms/trade-access/protocol/openid-connect/token' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d grant_type=client_credentials \
  -d client_id=trade-access-admin-client \
  -d client_secret="$ADMIN_CLIENT_SECRET")

echo "$TOKEN_RESPONSE"
```

提取并查看Token载荷：

```bash
ACCESS_TOKEN=$(printf '%s' "$TOKEN_RESPONSE" | \
  python3.12 -c "import json,sys; print(json.load(sys.stdin)['access_token'])")

ACCESS_TOKEN="$ACCESS_TOKEN" python3.12 -c "import base64,json,os; p=os.environ['ACCESS_TOKEN'].split('.')[1]; p += '=' * (-len(p) % 4); print(json.dumps(json.loads(base64.urlsafe_b64decode(p)), indent=2, ensure_ascii=False))"
```

确认：

```text
azp = trade-access-admin-client
aud 包含 trade-access-api
resource_access.trade-access-api.roles 包含 trade-access-admin
```

验证完成后清除临时变量：

```bash
unset ADMIN_CLIENT_SECRET TOKEN_RESPONSE ACCESS_TOKEN
```

## 7. 配置生产环境变量

测试环境可以使用`python3.12 scripts/configure_runtime.py`生成项目内的
`.runtime/trade-access.env`并由启动脚本自动加载。生产环境仍建议使用下面的
`/etc/trade-access/trade-access.env`和systemd `EnvironmentFile`，便于权限控制、备份和
配置审计。

### 7.1 创建环境文件

仓库已经提供无密码模板。将它安装到 `/etc` 后再填写真实值：

```bash
sudo install \
  -o root \
  -g ansiblerun \
  -m 0640 \
  /opt/trade-access/config/production/trade-access.env.example \
  /etc/trade-access/trade-access.env

sudo vi /etc/trade-access/trade-access.env
```

写入：

```ini
TRADE_ACCESS_API_AUTH_ENABLED=true

TRADE_ACCESS_API_DATABASE_PATH=/var/lib/trade-access/api/jobs.sqlite3
TRADE_ACCESS_API_RUNNER_PRIVATE_DATA_DIR=/var/lib/trade-access/runner
TRADE_ACCESS_API_JOB_TMP_ROOT=/var/lib/trade-access/jobs

TRADE_ACCESS_API_KEYCLOAK_SERVER_URL=https://keycloak.example.internal
TRADE_ACCESS_API_KEYCLOAK_REALM=trade-access
TRADE_ACCESS_API_KEYCLOAK_CLIENT_ID=trade-access-api
TRADE_ACCESS_API_KEYCLOAK_USER_ROLE=trade-access-user
TRADE_ACCESS_API_KEYCLOAK_ADMIN_ROLE=trade-access-admin

TRADE_ACCESS_API_KEYCLOAK_ADMIN_CLIENT_ID=trade-access-provisioner
TRADE_ACCESS_API_KEYCLOAK_ADMIN_CLIENT_SECRET=替换为ProvisioningClientSecret

TRADE_ACCESS_API_KEYCLOAK_HTTP_TIMEOUT_SECONDS=5
TRADE_ACCESS_API_KEYCLOAK_JWKS_CACHE_SECONDS=300
TRADE_ACCESS_API_KEYCLOAK_TOKEN_REFRESH_LEEWAY_SECONDS=30
```

防火墙目标、并发数和子任务重试次数已经放在 `group_vars/all.yml` 的
`trade_access_api` 中，不要在环境文件重复配置。兼容环境变量仍可覆盖 YAML，但
两处同时存在时会以环境变量为准。该环境文件只保存 API/Keycloak 运行参数和
密钥，不再保存防火墙管理 IP、账号或密码。

如果Keycloak使用企业内部CA，增加：

```ini
TRADE_ACCESS_API_KEYCLOAK_CA_CERT=/etc/trade-access/internal-ca.pem
```

安装CA文件：

```bash
sudo install -o root -g ansiblerun -m 0640 internal-ca.pem /etc/trade-access/internal-ca.pem
```

再次确认权限：

```bash
sudo chmod 0640 /etc/trade-access/trade-access.env
sudo chown root:ansiblerun /etc/trade-access/trade-access.env
```

禁止把该环境文件提交到Git或打入发布包。

### 7.2 验证环境变量

```bash
sudo -u ansiblerun bash -c '
  set -a
  source /etc/trade-access/trade-access.env
  set +a
  cd /opt/trade-access

'
```

期望最后一行是：

```text
True
```

## 9. 使用systemd运行API和Worker

创建：

```bash
sudo vi /etc/systemd/system/trade-access.service
```

内容：

```ini
[Unit]
Description=Trade Access API and Worker
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=ansiblerun
Group=ansiblerun
WorkingDirectory=/opt/trade-access
EnvironmentFile=/etc/trade-access/trade-access.env
Environment=PYTHONUNBUFFERED=1
ExecStart=/opt/trade-access/.venv/bin/python scripts/run_services.py --host 127.0.0.1 --port 8000 --poll-interval 0.5
Restart=always
RestartSec=5
TimeoutStopSec=30
KillSignal=SIGTERM
UMask=0027
NoNewPrivileges=true
PrivateTmp=false
ProtectSystem=full
ProtectHome=read-only
ReadWritePaths=/var/lib/trade-access /var/log/trade-access /tmp

[Install]
WantedBy=multi-user.target
```

说明：

- `PrivateTmp=false`是为了兼容当前Ansible和SSH临时目录行为。
- 防火墙私钥位于`/home/ansiblerun/.ssh`，所以使用`ProtectHome=read-only`。
- FastAPI只监听`127.0.0.1:8000`，由HTTPS反向代理对外提供服务。

加载并启动：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now trade-access.service
```

查看状态：

```bash
sudo systemctl status trade-access.service
sudo journalctl -u trade-access.service -f
```

本机健康检查：

```bash
curl -fsS http://127.0.0.1:8000/healthz
```

期望：

```json
{"status":"ok"}
```

## 10. 配置HTTPS反向代理

生产环境必须使用HTTPS，因为`X-API-Key`包含Client Secret。

以下为Nginx示例。证书路径按公司PKI调整。

```nginx
server {
    listen 443 ssl;
    server_name trade-access.example.internal;

    ssl_certificate     /etc/pki/tls/certs/trade-access.crt;
    ssl_certificate_key /etc/pki/tls/private/trade-access.key;
    ssl_protocols TLSv1.2 TLSv1.3;

    client_max_body_size 1m;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_connect_timeout 10s;
        proxy_read_timeout 120s;
    }

    # 建议只允许管理网访问管理员界面和管理员API。
    location ~ ^/(admin-ui|api/v1/admin/) {
        allow 192.168.5.0/24;
        deny all;

        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_connect_timeout 10s;
        proxy_read_timeout 120s;
    }
}
```

检查并启动：

```bash
sudo nginx -t
sudo systemctl enable --now nginx
sudo systemctl reload nginx
```

如果启用SELinux，允许Nginx连接本机后端：

```bash
sudo setsebool -P httpd_can_network_connect 1
```

只向需要的内网开放443，不建议直接开放8000。

```bash

  https://trade-access.example.internal/api/v1/trade-access/me
```

```bash
curl -i -X POST \
  https://trade-access.example.internal/api/v1/trade-access/allow \
  -H "Content-Type: application/json" \
  -H "X-API-Key: $USER_API_KEY" \
  -d '{
    "target_ip": "192.168.66.0",
    "mask": 24,
    "ports": [12001],
    "description": "production authorization check"
  }'
```

期望：

```text
HTTP 403
```

### 12.5 真实防火墙变更验收

1. allow
2. 查询任务直到`successful`
3. 防火墙侧确认地址、application和端口
4. deny
5. 防火墙侧确认地址和相关application已删除

验收完成后清除终端变量：

```bash
unset ADMIN_API_KEY USER_API_KEY
```

```bash

  /var/lib/trade-access/api/jobs.sqlite3 \
```

期望：


### 13.3 数据库恢复

```bash
sudo systemctl stop trade-access.service

sudo -u ansiblerun cp \
  /var/backups/trade-access/jobs-YYYYMMDD-HHMMSS.sqlite3 \
  /var/lib/trade-access/api/jobs.sqlite3

sudo chown ansiblerun:ansiblerun /var/lib/trade-access/api/jobs.sqlite3
sudo systemctl start trade-access.service
```

恢复后立即执行健康检查和权限查询。

## 16. 安全基线

生产上线前必须确认：

- `TRADE_ACCESS_API_AUTH_ENABLED=true`
- API只通过HTTPS访问
- 8000端口不直接暴露给普通用户网段
- `/admin-ui`和`/api/v1/admin/**`限制到管理网
- Provisioning Secret只存在于服务端受限环境文件
- 管理员和用户`X-API-Key`不进入日志
- 每个调用方使用独立Client，不共享Client Secret
- 普通用户只分配必要接口权限，目标IP由接口按合法 IPv4 `/32` 校验
- Provisioning Client不使用`realm-admin`
- 防火墙使用专用SSH用户和专用私钥
- 操作系统、Python依赖和Keycloak有升级计划
- Keycloak和API节点启用时间同步
- 数据库、配置和密钥有备份及恢复演练

## 17. 上线回滚方案

出现以下情况时应停止生产变更：

- Keycloak Token无法通过`aud`或角色验证
- Provisioning Client无法创建或修改Client
- Worker无法SSH登录防火墙
- 测试IP的allow或deny与预期不一致
- 队列持续阻塞
- SQLite出现完整性错误

停止服务：

```bash
sudo systemctl stop trade-access.service
```

应用回滚：

1. 恢复上一版本代码目录。
2. 恢复兼容的数据库备份。
3. 恢复上一版环境文件。
4. 执行Playbook语法检查。
5. 启动服务并执行健康检查。
6. 使用测试IP完成allow/deny回归。

防火墙配置异常时，应由网络管理员根据设备现状执行独立回滚，不能仅依赖API数据库状态。
