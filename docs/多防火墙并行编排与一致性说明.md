# 多防火墙并行编排与一致性

## 运行边界

业务变更接口不携带防火墙代号。`POST /allow`、`POST /allow/ip`、
`POST /allow/ports`、`POST /deny/ports`、`POST /deny/ip` 和 `POST /deny`
每次都创建一个父任务，父任务的目标来自 `group_vars/all.yml`：

```yaml
trade_access_api:
  firewall_targets:
    - "PG-FW"
    - "PG-FW-1"
    - "IDC-FW"
  firewall_parallel_workers: 3
  firewall_child_max_attempts: 2
  firewall_reconcile_retry_seconds: 30
```

测试环境保持：

```yaml
trade_access_api:
  firewall_targets:
    - "TEST-FW"
  firewall_parallel_workers: 3
  firewall_child_max_attempts: 2
  firewall_reconcile_retry_seconds: 30
```

历史 `TRADE_ACCESS_API_FIREWALL_TARGETS`、
`TRADE_ACCESS_API_FIREWALL_PARALLEL_WORKERS` 和
`TRADE_ACCESS_API_FIREWALL_CHILD_MAX_ATTEMPTS` 仍可覆盖 YAML 值，但正常部署无需
重复配置。API 与 worker 重启后读取同一份配置。

三台设备的完整生产 profile 已注释保存在
[`../group_vars/all.yml`](../group_vars/all.yml) 的
`BEGIN_PRODUCTION_CONFIG` 区块，连接 IP、账号和密码直接填写在对应 profile。

| 防火墙 | IP 操作空间 | Application / Application Group 空间 |
| --- | --- | --- |
| `PG-FW` | `public`、`private`、`Internet` | `private` |
| `PG-FW-1` | `public` | `public` |
| `IDC-FW` | `private`、`Internet` | `private` |

## 父子任务

一个父任务内部，各防火墙子任务使用独立 ansible-runner 目录并行执行。每轮父任务
执行仍使用全局编排锁；若有节点失败，父任务写入下一次重试时间后立即释放锁。调度器
允许其他 IP 的任务继续执行，但同一 IP 的后续任务必须等待前序父任务收敛，避免期望
状态乱序。

执行顺序：

1. 优先从 `desired_access_states` 读取该 IP 的业务期望基线；已有基线、任务重试和
   进程恢复均不执行预检。仅首次接管一个未知 IP 时，并行查询所有节点建立一次基线。
2. 根据业务期望基线和本次动作计算新期望状态，并递增状态版本。
3. 将新期望状态写入 `desired_access_states`，再并行执行各防火墙子任务。
4. 普通 runner 失败后不插入状态查询，直接等待该失败节点的下一次幂等重试；已经
   执行完成的节点不重复配置。
5. 每轮只对未完成的节点执行一次配置，`attempt_count` 在整个父任务生命
   周期内累计，不能因重新入队而清零或重新获得尝试次数。
6. 所有节点不再需要重试后，父任务只发起一轮并行最终验证；从每台设备的实时完整
   状态中提取本次 `target_ip` 的 IP 状态和完整端口集合，与同一 `desired_state` 比较。
7. 第一次可恢复失败后，父任务进入 `reconciling`，在
   `firewall_reconcile_retry_seconds` 后执行最后一次重试。累计达到
   `firewall_child_max_attempts` 后仍会执行一次最终验证，因为 runner 的后置步骤失败时
   设备配置可能已经生效；实测仍不匹配才进入 `failed`。
8. 设备明确返回“user-defined Application 达到上限”等不可自动恢复错误时，不等待
   下一轮，父任务和对应子任务立即进入 `manual_intervention_required`。

父任务最终状态：

- `successful`：所有目标均已实时校验为期望状态。
- `reconciling`：至少一个节点首次执行未收敛，父任务等待最后一次自动重试。
- `failed`：累计两次仍未收敛，或无法建立安全初始基线。
- `manual_intervention_required`：设备容量等明确不可自动恢复问题，自动重试已停止。

`GET /api/v1/trade-access/jobs/{job_id}` 返回 `desired_state`、`state_version` 和
每台防火墙的 `target_results`，包括变更前、期望、实测状态、尝试次数和错误。

如果 worker 在部分目标成功后退出，未完成父任务不会丢失。worker 重启后会重新
认领该任务，复用同一状态版本；已经完成配置的目标等待统一验证，尚未完成的目标
继续执行，不会重新做完整预检。

该方案提供有限自动恢复和明确的差异状态，不把三台独立设备伪装成支持原子提交的
分布式事务。自动重试耗尽或设备返回不可恢复错误后，可通过 `check` 接口定位节点并
人工纠正，不会继续每 30 秒无限执行。

## 全量查询

全量快照接口并行实时查询 `trade_access_api.firewall_targets` 中的所有防火墙，
查询前会取得与父任务相同的全局编排锁，避免读取到一个多设备变更的中间状态。
每台设备先按自己的虚拟系统拓扑计算有效 IP 或 IP:Port，再比较逻辑集合：

- 全部一致：HTTP `200`，返回干净的 `items`，并标记
  `consistency_status=consistent`。
- 查询都成功但集合不同：HTTP `409`，返回每台防火墙的缺失/额外项，标记
  `consistency_status=drifted`。
- 任一设备查询失败：HTTP `503`，标记
  `consistency_status=incomplete`，不把剩余设备结果冒充全量结果。
- 存在 `reconciling` 父任务：HTTP `409`，不提供普通全量清单；使用 `check` 查看
  三台原始状态和人工纠错建议。

全量查询与任务校验的边界不同：全量查询比较所有有效数据；任务完成校验只比较该
任务目标 IP 的完整业务状态。

## 人工一致性检查

`GET /api/v1/trade-access/firewall/check` 在同一个全局编排锁内，并行对每台设备执行
一次 `state` 查询，同时获得 IP 与 IP:Port 集合。接口返回逐项存在/缺失节点、逐台
缺失/多余数据以及按严格多数节点生成的人工纠错建议。建议动作只用于排查，不会
自动提交到设备；执行前仍需结合业务期望状态确认新增还是回退。

- 一致或漂移：HTTP `200`，查看 `overall_status`。
- 任一设备查询失败：HTTP `503`、`overall_status=incomplete`，不生成建议。
- 偶数节点各占一半：差异标记为 `ambiguous`，不生成建议。
