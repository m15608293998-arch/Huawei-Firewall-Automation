# 多防火墙并行编排与一致性

## 运行边界

业务变更接口不携带防火墙代号。`POST /allow`、`POST /allow/ip`、
`POST /allow/ports`、`POST /deny/ports`、`POST /deny/ip` 和 `POST /deny`
首次受理时创建一个父任务，父任务的目标来自 `group_vars/all.yml`；同一用户用相同
`client_request_id` 重发相同请求时返回原任务，相同键对应不同内容时返回 `409`：

```yaml
trade_access_api:
  firewall_targets:
    - "PG-FW"
    - "PG-FW-1"
    - "IDC-FW"
  firewall_parallel_workers: 3
  firewall_child_max_attempts: 2
  firewall_reconcile_retry_seconds: 3
```

测试环境保持：

```yaml
trade_access_api:
  firewall_targets:
    - "TEST-FW"
  firewall_parallel_workers: 3
  firewall_child_max_attempts: 2
  firewall_reconcile_retry_seconds: 3
```

历史 `TRADE_ACCESS_API_FIREWALL_TARGETS`、
`TRADE_ACCESS_API_FIREWALL_PARALLEL_WORKERS` 和
`TRADE_ACCESS_API_FIREWALL_CHILD_MAX_ATTEMPTS` 仍可覆盖 YAML 值，但正常部署无需
重复配置。API 与 worker 重启后读取同一份配置。

三台设备的完整生产 profile 已注释保存在
[`../group_vars/all.yml`](../group_vars/all.yml) 的
`BEGIN_PRODUCTION_CONFIG` 区块，连接 IP、账号和密码直接填写在对应 profile。

| 防火墙 | IP 操作空间 | Application / Application Group 空间 |
| --- | --- | --- |
| `PG-FW` | `public`、`private`、`Internet` | `private` |
| `PG-FW-1` | `public` | `public` |
| `IDC-FW` | `private`、`Internet` | `private` |

## 父子任务

一个父任务内部，各防火墙子任务使用独立 ansible-runner 目录并行执行。父任务从开始
配置到最终验证结束始终持有全局编排锁。若有节点首次配置失败，父任务不重新入队，
而是在锁内短暂退避后只重试失败节点；后来的变更和全量查询不能插入部分节点已成功、
部分节点待修复的窗口。只有首次基线查询失败时会写入 `next_attempt_at` 并释放队列，
因为这时尚未向任何防火墙写入配置，不存在多节点中间状态。

执行顺序：

1. 优先从 `desired_access_states` 读取该 IP 的业务期望基线；已有基线或任务自身
   已有期望状态时，重试和进程恢复均不执行预检。仅首次接管未知 IP 时，并行查询
   所有节点建立基线；查询失败按持久化预检计数有限重试。完整 `deny` 直接采用
   “全部不存在”的绝对目标，无账本或节点已有差异时也不要求建立公共基线。
2. 根据业务期望基线和本次动作计算新期望状态，并递增状态版本；完整 `deny` 固定
   为 `ip_present=false, ports=[]`。
3. 将新期望状态写入 `desired_access_states`，再并行执行各防火墙子任务。端口任务将
   完整期望端口集合传给 Role；每次执行按设备现状重新计算差量，补回中断时丢失的
   应保留端口并移除多余端口。IP 接口仍只修改地址成员。
4. 普通 runner 首次失败后不插入状态查询。父任务进入 `reconciling`，在内部短暂
   退避后直接对失败节点做最后一次幂等重试；已经执行完成的节点不重复配置。
5. `attempt_count` 在整个父任务生命周期内累计。每个防火墙节点最多执行
   `firewall_child_max_attempts` 次，不能因进程恢复而清零或重新获得尝试次数。
6. 所有节点的 runner 均成功后，父任务发起并行最终验证；逐虚拟系统检查本次 IP 的
   地址成员，并检查原始应用、端口、IP 绑定及组成员。撤销要求所有地址成员和目标
   应用/组成员均不存在，不再使用只展示有效配置的 IP/端口清单证明清理完成。
   完整撤销在每台设备删除前仍检查对象的实际 IP/掩码归属和详情完整性，错绑其他 IP
   或解析不完整时拒绝删除；其他节点可能已完成，保留各节点结果供人工处理。
7. 第一次可恢复配置失败后，父任务在锁内等待
   `firewall_reconcile_retry_seconds`（当前为 3 秒），然后执行最后一次重试，不写
   `next_attempt_at`，也不让其他父任务插队。每次 worker 下发均要求执行配置所启用的
   commit/save，即使增删计划已无变化，也会补做最终提交与保存。累计达到
   `firewall_child_max_attempts` 后 runner 仍失败，则进入 `failed`；配置已存在不能
   覆盖提交或保存失败。进程在最后一次执行中断且未记录成功时同样保守判为失败。
8. 设备明确返回“user-defined Application 达到上限”等不可自动恢复错误时，不等待
   下一轮，父任务和对应子任务立即进入 `manual_intervention_required`。
9. 首次认领时持久化父任务截止时间，预检、退避、Runner、最终验证共享预算；恢复或
   重试不重新计时。各设备调用在真正开始时计算剩余预算，线程池排队不能延长时限。

父任务最终状态：

- `successful`：所有目标均已成功完成执行及所启用的提交/保存，并实时校验为期望状态。
- `reconciling`：配置已经开始时，父任务正在内部短暂退避或执行最后一次修复；首次
  基线查询失败时，则表示尚未写配置并等待计划重试。
- `failed`：配置尝试耗尽、预检达到次数上限、总预算耗尽，或无法建立安全初始基线。
- `manual_intervention_required`：设备容量等明确不可自动恢复问题，自动重试已停止。
- `canceled`：配置准备前被所有者或管理员取消，父子任务均停止推进。

`GET /api/v1/trade-access/jobs/{job_id}` 返回 `desired_state`、`state_version`、
`deadline_at`、`precheck_attempt_count` 和
每台防火墙的 `target_results`，包括变更前、期望、实测状态、尝试次数和错误。

如果 worker 在部分目标成功后退出，未完成父任务不会丢失。worker 重启后会重新
认领该任务，复用同一状态版本；已经完成配置的目标等待统一验证，尚未完成的目标
继续执行，不会重新做完整预检。

该方案提供有限自动恢复和明确的差异状态，不把三台独立设备伪装成支持原子提交的
分布式事务。自动重试耗尽或设备返回不可恢复错误后，可通过 `check` 接口定位节点并
人工纠正；每个节点最多执行两次，不会无限重试。

## 截止时间与安全取消

环境变量 `TRADE_ACCESS_API_JOB_TIMEOUT_SECONDS` 默认 1800 秒，从首次认领开始，
排队等待不计入；重启后继续使用原截止时间。单次 Runner、查询和锁等待分别通过
`TRADE_ACCESS_API_RUNNER_TIMEOUT_SECONDS`（900）、
`TRADE_ACCESS_API_SNAPSHOT_TIMEOUT_SECONDS`（300）、
`TRADE_ACCESS_API_RUNNER_LOCK_TIMEOUT_SECONDS`（10）配置，均受剩余预算限制。
CLI 分页、确认、busy 重试和 commit 轮询不能重置预算，Runner 超时会终止子进程组。
总预算耗尽后父任务标记 `failed`、`runner_status=timed_out`；若已下发配置，需根据
保留的逐台结果人工核对部分变更。

基线查询默认包含首次在内最多尝试 3 次，由
`TRADE_ACCESS_API_PRECHECK_MAX_ATTEMPTS` 配置。失败退避从
`firewall_reconcile_retry_seconds` 开始倍增，最多 60 秒，并受剩余总预算限制；
次数持久化，worker 重启不会清零。次数耗尽进入 `failed`，
`runner_status=precheck_attempt_limit_reached`，后续同 IP 任务不再受它阻塞。

所有者调用 `POST /api/v1/trade-access/jobs/{job_id}/cancel`，管理员使用
`POST /api/v1/admin/trade-access/jobs/{job_id}/cancel`。排队、只读预检和等待预检重试
时可取消；开始准备期望账本后返回 `409`。取消与准备配置通过数据库原子迁移竞争，
取消获胜后，晚返回的预检不能恢复父子任务或触发写入。正在执行的只读查询会在完成
或超时后退出，期间编排锁仍由该预检持有。重复取消返回相同终态；重做任务需要新
`client_request_id`。

## 全量查询

全量快照接口并行实时查询 `trade_access_api.firewall_targets` 中的所有防火墙，
查询前会取得与父任务相同的全局编排锁，避免读取到一个多设备变更的中间状态。
锁等待超过预算返回 `503`，不会无限占用 API 线程；总查询预算包含锁等待和所有节点。
每台设备先按自己的虚拟系统拓扑计算有效 IP 或 IP:Port，再比较逻辑集合：

- 全部一致：HTTP `200`，返回干净的 `items`，并标记
  `consistency_status=consistent`。
- 查询都成功但集合不同：HTTP `409`，返回每台防火墙的缺失/额外项，标记
  `consistency_status=drifted`。
- 任一设备查询失败：HTTP `503`，标记
  `consistency_status=incomplete`，不把剩余设备结果冒充全量结果。
- 存在 `reconciling` 父任务：HTTP `409`，不提供普通全量清单；使用 `check` 查看
  三台原始状态和人工纠错建议。

全量查询与任务校验的边界不同：全量查询比较所有有效数据；任务完成校验只比较该
任务目标 IP 的完整业务状态。

## 人工一致性检查

`GET /api/v1/trade-access/firewall/check` 在同一个全局编排锁内，并行对每台设备执行
一次 `state` 查询，同时获得 IP 与 IP:Port 集合。接口返回逐项存在/缺失节点、逐台
缺失/多余数据以及按严格多数节点生成的人工纠错建议。建议动作只用于排查，不会
自动提交到设备；执行前仍需结合业务期望状态确认新增还是回退。

- 一致或漂移：HTTP `200`，查看 `overall_status`。
- 任一设备查询失败：HTTP `503`、`overall_status=incomplete`，不生成建议。
- 偶数节点各占一半：差异标记为 `ambiguous`，不生成建议。
