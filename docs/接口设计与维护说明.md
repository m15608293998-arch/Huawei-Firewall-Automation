# Trade Access 核心接口设计

> 面向后端维护人员，只说明核心业务接口和关键算法。
> 核对基线：2026-07-17，`main` 提交 `ebf4594`。

## 1. 接口概览

统一认证：

```http
Authorization: Bearer <Keycloak Access Token 或 sk-<offline_token>>
```

| 接口 | 权限 | 作用 |
| --- | --- | --- |
| `POST /api/v1/trade-access/allow/ip` | `firewall.ip.allow` | 放行 IP |
| `POST /api/v1/trade-access/deny/ip` | `firewall.ip.deny` | 删除 IP |
| `POST /api/v1/trade-access/allow/ports` | `firewall.ports.allow` | 增加端口 |
| `POST /api/v1/trade-access/deny/ports` | `firewall.ports.deny` | 删除端口 |
| `GET /api/v1/trade-access/firewall/snapshot/ips` | `firewall.snapshot.read` | 全量查询有效 IP |
| `GET /api/v1/trade-access/firewall/snapshot/ports` | `firewall.snapshot.read` | 全量查询有效 IP:Port |

IP 接口 Body：

```json
{"target_ip":"192.168.66.1","mask":32,"description":"optional"}
```

端口接口 Body：

```json
{"target_ip":"192.168.66.1","mask":32,"ports":[12001,12002]}
```

仅支持 IPv4 `/32`；端口范围 1 到 65535，单次最多 256 个，自动去重排序。
`client_request_id` 已删除，每次 POST 都会生成新的 `job_id`。

变更接口写入 SQLite 后返回 `202`，由 Worker 串行执行。最终结果查询：

```http
GET /api/v1/trade-access/jobs/{job_id}
```

任务状态为：

```text
pending -> running -> successful
                   -> failed
```

`202` 只代表任务已入队，不代表防火墙已修改成功。任务详情中的
`runner_status`、`runner_rc` 和 `error_message` 是主要排错字段。

组合接口 `POST /allow` 等于“放行 IP + 增加端口”；`POST /deny` 等于“删除该
IP 的全部 Application/端口 + 删除 IP”。

## 2. IP 与端口操作

### IP

- `allow/ip`：将 IP 加入 `public`、`Internet`、`private` 三个 vSystem 的
  `TraderServers-DirectAccess-IPs`。
- `deny/ip`：先确认该 IP 已无业务 Application 端口，再从三个 Address Set
  删除；仍有端口时任务失败。

### 端口

- `allow/ports`：先确认 IP 已存在于三个 Address Set，再在 `private` vSystem
  增量维护 Application。
- `deny/ports`：只删除实际存在的指定端口；Rule 为空则删除 Rule，
  Application 为空则移出组并删除对象。

Role 会先读取设备现状，再生成增量计划。请求中的端口已经处于目标状态时不重复
修改；发生变更后会重新查询并验证 Application，最后统一执行 commit/save。

Application 规则：

```text
名称: UD_TServe_<IP>、UD_TServe_<IP>_2、UD_TServe_<IP>_3 ...
组名: UDG_TradeServers
容量: 4 ports/rule，8 rules/application，32 ports/application
```

## 3. 删除后的端口插空

新增端口按升序逐个处理：

1. 先找第一个少于 4 个端口的已有 Rule，直接追加。
2. 已有 Rule 都满时，在第一个未满 8 条 Rule 的 Application 中创建 Rule。
3. Rule 编号使用最小空缺编号，例如 Rule 2 被删除后优先复用 Rule 2。
4. 所有 Application 都满时，创建最小可用后缀 Application。
5. 不跨 Rule 或 Application 搬动、压缩已有端口。

示例：

```text
原状态: Rule 1=[12001,12002]，Rule 3=[12010,12011,12012,12013]
新增:   [13001,13002,13003]
结果:   Rule 1=[12001,12002,13001,13002]，Rule 2=[13003]，Rule 3 不变
```

删除端口时：

- 删除 Rule 尾部端口：直接 `undo port`。
- 删除 Rule 中间端口：重写当前 Rule，即撤销旧端口后加回保留端口，
  对应 `replace_rule_ports`。
- Rule 变空：删除 Rule；Application 变空：删除 Application。

规划实现位于
`roles/usg6000e_trade_access/files/extract_usg_application_names.py` 的
`build_application_plan()`、`_plan_add_port()`、`_plan_remove_ports()`。

## 4. Huawei 防火墙 GUI 端口显示为 0

### 4.1 已观察到的现象

设一条 Rule 当前包含 `x` 个端口，端口位置依次为 `1 ... x`。当满足：

```text
2 <= x <= 4
1 <= i < x
```

即使用 `undo port` 删除的端口位于第 `i` 个非尾部位置时。在已观察案例中，删除
命令和 `engine configuration commit` 均执行成功，但防火墙 GUI 会在原第 `i`
个位置显示 `0`。

目前可以确认的是 GUI 显示异常；“设备内部仍保留原端口槽位，并用 0 作为空位标识”
只是对现象的推测，尚无厂商文档或设备底层证据支持，不能作为确定结论。

### 4.2 当前处理方式

规划器区分尾部删除和非尾部删除：

- 删除的是 Rule 尾部端口时，继续使用简单的 `undo port`。
- 删除的是 Rule 中间端口时，生成 `replace_rule_ports`：
  1. 在同一个 Application、同一条 Rule 中撤销全部旧端口。
  2. 将目标删除端口以外的端口重新加入该 Rule。
  3. 不修改其他 Rule，也不跨 Rule 重新排序端口。
  4. 重新查询 Application，确认最终端口集合与计划一致后再 commit/save。

例如 Rule 为 `[12001, 12002, 12003]`，删除 `12002` 时，实际生成的逻辑相当于：

```text
undo port 12001
undo port 12002
undo port 12003
port 12001
port 12003
```

这样重建当前 Rule，目标是清除非尾部删除产生的空槽位；效果仍需结合下述设备测试
确认。

### 4.3 尚未确认的流量风险

不能仅根据“最终 commit 前已把无关端口加回”就认定业务一定不受影响。需要确认
Huawei 设备在 `engine configuration commit` 前使用的是候选配置还是实时配置，
以及 Application Rule 的 `undo port` 是否会立即影响数据面。

当前方案必须完成以下设备验证：

1. 对 `x=2、3、4` 的 Rule 分别测试首位、中间位置和尾部端口删除。
2. 在执行 `undo`、重新添加、验证查询和最终 commit 的整个过程中，持续探测未删除
   端口的真实业务流量。
3. 分别核对 CLI 查询结果、GUI 显示和实际连通性，不能只看任务成功状态。
4. 模拟重建过程中 SSH 中断或命令失败，确认无关端口的恢复方法。
5. 确认测试结果后，再决定是否将 `replace_rule_ports` 作为生产环境长期方案。

在以上验证完成前，应将该处理视为“解决 GUI 0 显示问题的待验证方案”，不能承诺
删除中间端口时对其他端口完全无瞬时影响。

## 5. 长效 SK

创建流程：

1. `POST /api/v1/api-keys/authorize`，Body 为 `{"label":"postman"}`。
2. 接口返回 Keycloak Authorization Code + PKCE 授权地址。
3. Keycloak 回调 `GET /api/v1/auth/offline/callback`。
4. 原始凭据只返回一次，固定格式为 `sk-<offline_token>`。

认证时，后端使用 offline token 向 Keycloak 换取短期 Access Token，再执行正常的
JWT、角色和本地权限校验。SQLite 保存 SK 哈希及加密后的当前 offline token；
Keycloak 轮换 `refresh_token` 后会覆盖保存新 token。

`TRADE_ACCESS_API_OFFLINE_API_KEY_TOKEN_ENCRYPTION_KEY` 必须长期保持不变。

```http
GET    /api/v1/api-keys
DELETE /api/v1/api-keys/{key_id}
```

实现位于 `api/offline_api_keys.py` 和 `api/auth.py`。

## 6. 全量查询

全量查询实时执行防火墙 CLI，不读取任务数据库，不创建 `job_id`。

- `snapshot/ips`：只返回同时存在于 `public`、`Internet`、`private` 三个
  Address Set 中的精确 `/32` IP，即三个空间的交集。
- `snapshot/ports`：在上述 IP 交集基础上，只返回 `UDG_TradeServers` 内
  Application Rule 真实绑定的 `(ip, port)`。

端口结果按 IP、端口排序并全局去重，不根据 Application 名推导 IP。
`GET /api/v1/trade-access/firewall/snapshot` 是兼容入口，当前等同
`snapshot/ports`。

快照是同步接口，并与变更任务共享 `firewall_runner.lock`，同一时间只运行一条
防火墙执行链。
