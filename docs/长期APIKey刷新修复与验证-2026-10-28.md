**P2-18：长期 API Key 刷新并发修复，2026-10-28**

分支：`codex/fix-offline-key-refresh`，基于本地 `main` 的 `75c96dc`。
仅处理 P2-18；P2-17 的队列/文件容量和 P2-08 的查询权限按用户要求不修改。

**修复行为**

- 进程内按 Key 合并在途刷新，只在读取缓存和登记刷新时短暂持锁。网络请求、JWT
  验证和令牌落库均在锁外完成，其他 Key 的缓存认证和独立刷新不再等待慢请求。
- 同一组等待者共享成功或失败结果，等待不超过 Keycloak HTTP 超时配置。等待
  超时返回 `503`，不取消正在进行的刷新；刷新结束后允许后续请求重试。
- 同机多 API 进程通过共享 SQLite 数据库旁的按 Key 文件锁协调；拿锁后重新读取
  当前 Token，短期 Access Token 加密保存并复用。新进程正常验签、检查 client/sub，
  缓存有效期保持在 Token 到期前 30 秒；验签不通过时重新向 Keycloak 获取 Token。
- 轮换后的 refresh token 在 JWT 验证前保存，避免 JWKS 暂时不可用时丢失轮换链。
  写回检查原 Token 版本及撤销状态，过时响应不能覆盖新版本；写入失败不报告认证
  成功。API Key 返回格式和既有加密密钥保持，公共接口不返回共享缓存字段。
- 认证返回前重新检查 Key 撤销及用户启用状态。撤销无需等待刷新网络请求。
  进程退出自动释放内核文件锁，其他进程可重新获取。

**验证**

- 原实现的四个反例均失败：有效缓存的其他 Key 被阻塞、其他 Key 的独立刷新被
  阻塞、撤销等待慢刷新，以及 JWKS 故障前收到的新 refresh token 未保存。
- 新增 16 项专项回归；认证、迁移及新增专项共 31 项通过。
- 全量 **322 项测试通过**（37.333 秒），包括已有 JWT、JWKS、权限、任务、查询、
  Worker 和审计回归。Python 语法和 Git 差异空白检查通过。
- 使用真实线程和两个独立 spawn 进程验证并发。同 Key 只发一次模拟 Token 请求，
  失败组共享一次请求；缓存认证和不同 Key 刷新在另一 Key 阻塞期间完成。
- 覆盖等待超时、刷新期间撤销/禁用、进程退出释放锁、缓存到期与 Keycloak 断网、
  轮换写入失败、缓存写入失败后继续使用已保存的轮换 Token，以及版本冲突。
- 验证共享缓存加密、公共响应无缓存字段、新进程仍执行验签，以及旧表自动加列。
  另补反例确认：共享 Token 的签名密钥失效后，不会一直被旧缓存阻止获取新 Token。

所有测试使用临时数据库、模拟 Keycloak 响应和本地进程；本轮未连接真实 Keycloak
或防火墙，未改动 `192.168.6.54` 和真实 `.runtime` 数据。实际 Keycloak 的 Token
轮换、重用策略仍需在部署环境验收。

**部署与恢复边界**

所有 API 进程一起升级并使用同一数据库路径、锁目录和 Token 加密密钥。数据库
自动增加 `encrypted_access_token` 和 `access_token_usable_until`，旧 SK 继续使用。
锁目录为 `<数据库文件名>.key-locks`，锁文件中不保存 Token；运行期间不能删除锁
文件，也不能与不参与本机制的旧版 API 混跑。

Keycloak 的远端轮换和 SQLite 的本地提交不能组成原子事务。若远端已消费旧 Token、
新 Token 尚未保存时进程退出或写盘失败，本轮保证不报告认证成功；旧 Token 是否
仍可恢复取决于 Keycloak 的重用策略。旧 Token 已被拒绝且新 Token 未落库时，需要
重新授权创建 Key。进程退出释放锁本身不能恢复尚未落库的远端响应。
