**P1-01：提交或保存失败，可以被最终查询改判为成功**

位置：[worker.py:704](/root/ansible-firewalld-automation/api/worker.py:704)、[access/main.yml:162](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/tasks/access/main.yml:162)。

`_verify_target()` 在查询结果匹配时，无论此前失败发生在哪一阶段，都允许将设备标为 `verified_after_runner_failure`，清空错误，最终将父任务标为 `successful`。但查询只核对配置中的 IP/端口，不证明安全引擎已提交成功，也不证明 `save` 已完成。

此外，每次 Role 运行都重新把 `firewall_mutated`、`application_mutated` 设为 false。第一次已改完配置、随后 commit/save 失败时，第二次可能发现无需增删，于是跳过 commit/save。这个路径也会报告成功。

复现：模拟设备已修改配置、两次 Runner 均返回失败，父任务仍为 `successful`，子任务保留 `runner_rc=2`，状态为 `verified_after_runner_failure`。引擎是否仍影响旧流量需真机验证；保存失败可能导致设备重启后失去变更，代码当前没有证明持久化成功。

修复方向：持久化每台设备的 apply、commit、save 阶段及未完成标记；重试必须补齐未完成阶段。只有能够归类为无关后处理失败的错误才可被配置查询覆盖。完成语义应同时覆盖配置、引擎提交和按配置要求进行的保存。

**P1-02：撤销校验使用“有效清单”，会隐藏残留虚拟系统和孤立应用**

位置：[extract_usg_trade_snapshot.py:315](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/files/extract_usg_trade_snapshot.py:315)、[extract_usg_trade_snapshot.py:370](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/files/extract_usg_trade_snapshot.py:370)、[worker.py:740](/root/ansible-firewalld-automation/api/worker.py:740)。

`ip_items` 只包含同时存在于全部配置虚拟系统的 IP；`port_items` 又只包含这些 IP 在指定组中的端口。Worker 用相同的投影视图做完整撤销验证。只要某一个虚拟系统已删除 IP，它就从清单中消失，其余虚拟系统的地址残留及应用残留也可能无法从该视图发现。

**P1-03：保存了完整期望状态，但执行和重试仍只重放增量请求**

位置：[worker.py:464](/root/ansible-firewalld-automation/api/worker.py:464)、[worker.py:578](/root/ansible-firewalld-automation/api/worker.py:578)、[runner_service.py:186](/root/ansible-firewalld-automation/api/runner_service.py:186)、[incremental_ports.cli.j2:31](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/templates/application/incremental_ports.cli.j2:31)。

Worker 在下发前更新 `desired_access_states`，失败后保留该状态；后续任务继续以它为基线。但 Runner 没有把完整 `desired_state` 转成下发计划，只传原始 action 和请求端口。因此“预期中有、设备上实际没加成功”的端口不会自动补齐；人工漂移也可能使后续任务持续失败。

复现一：第一次请求增加 12001，两次失败且设备未变；第二次请求增加 12002，设备只获得 12002，Worker 要求 `[12001,12002]`，重复增量操作仍不能收敛。

复现二：原 Rule 为 `[12001,12002,12003]`，删除中间的 12002 会先撤销全部旧端口。若撤销 12001 后中断，重试从当前残缺配置重建计划，最终期望变成 `[12003]`，不会恢复本应保留的 12001。最终校验可以发现不一致，但没有恢复机制；不能据此承诺其他业务端口不受影响。

修复方向：重试从“实测原始状态 → 此任务不可变完整期望状态”重新生成差量；对删除后重建 Rule 的流程持久化原始计划和应保留端口。为失败任务提供恢复、重新采纳人工状态或显式覆盖期望状态的受控入口，不能仅靠再次提交局部增删。

**P1-04：完整 deny 根据对象名删除，没有校验应用实际绑定的 IP**

位置：[remove_all_for_ip.yml:29](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/tasks/application/remove_all_for_ip.yml:29)、[remove_object.yml:31](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/tasks/application/remove_object.yml:31)。

端口增删流程会检查 `all_target_ips_match`；完整 deny 流程只通过命名模式找对象，再检查对象名和组成员，不查询并验证每条 Rule 的实际 IP/掩码。如果历史人工配置或漂移导致 `UD_TServe_A` 实际绑定 B，撤销 A 会直接删除为 B 提供服务的应用。

复现：名为 `UD_TServe_203.0.113.10`、实际 Rule 绑定 `203.0.113.20:443` 的对象仍会被删除发现逻辑选中；同一输入若进入端口变更校验，则会因 IP 不匹配被拒绝。实际删除路径的缺少校验由 Role 源码确认，未进行真实删除。

修复方向：所有破坏性操作前查询对象详情，确认 Rule 全部归属于目标 IP 和掩码；存在混合 IP、名称不符或详情解析不完整时转人工处理。对象命名只能用于发现，不能单独证明删除归属。

**P3-05：SSH 主机身份校验可作为后续加固，不阻塞本次上线**

位置：[run_usg_cli.py:135](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/files/run_usg_cli.py:135)。

命令固定包含 `StrictHostKeyChecking=no`、`UserKnownHostsFile=/dev/null`，且使用 `-F /dev/null`。应用没有验证连接对端是否为预期防火墙。用户已说明系统用于公司内部、无法访问互联网的环境；按此部署范围，本项降为 P3，不要求为本次上线修改 SSH 行为。

剩余风险的前提是攻击者已能劫持内部管理链路；不能仅从关闭校验推定这一攻击前提存在。无互联网访问本身不等同于内部链路不会被劫持，但是否需要防范应结合公司网络隔离和访问控制决定。后续如扩大网络访问范围，可部署受控 `known_hosts` 或固定设备主机密钥并启用严格校验。

**P1-06：未认证请求可反复触发 JWKS 网络刷新，并阻塞正常认证**

位置：[keycloak.py:39](/root/ansible-firewalld-automation/api/keycloak.py:39)、[keycloak.py:71](/root/ansible-firewalld-automation/api/keycloak.py:71)。

JWT 签名校验前，程序按不可信 `kid` 查询密钥。即使缓存未过期，只要 `kid` 不在缓存中就立即刷新 JWKS；该网络请求在共享锁内执行。攻击者无需有效签名，反复发送携带未知 `kid` 的 JWT 即可制造外部请求，并让正常认证等待同一把锁。仓库也没有配套的认证失败限流或刷新冷却。

复现：连续验证 5 个同样的伪造 JWT，发生 5 次 JWKS fetch；无需使用不同 `kid`。这证明了请求放大路径，未对真实 Keycloak 发起压力测试。

修复方向：设置全局刷新最小间隔、未知 kid 短期负缓存和合并刷新；不要让正常有效缓存读取等待无关的未知 kid 请求；结合入口限流与响应体/凭据长度上限验证资源边界。

**P1-07：直接同步脚本绕过父任务编排，只修改第一台设备**

位置：[reconcile_firewall_to_ip_ports.py:225](/root/ansible-firewalld-automation/scripts/reconcile_firewall_to_ip_ports.py:225)、[runner_service.py:82](/root/ansible-firewalld-automation/api/runner_service.py:82)。

该未跟踪脚本的快照查询覆盖配置中的所有防火墙，变更却调用 `run_trade_access(job)`，未指定 firewall_code。Runner 默认只选第一台设备。生产启用三台时，一次操作便可主动制造设备漂移，后续全量快照才发现失败，且没有回滚已改设备。

它还绕过 SQLite 任务、期望状态账本和父编排锁。单设备 Runner 锁只能串行一台设备的命令，不能防止该脚本插入其他父任务的多设备变更过程；脚本完成后，账本也可能仍指向旧状态。

复现：mock 截获一次 operation，只看到一次 Runner 调用且没有显式防火墙参数；默认选择当前配置的首台。此项仅在该脚本被纳入生产使用时构成上线阻塞；主 API 路径已显式传递设备代码。

修复方向：脚本通过业务 API 提交并等待任务，或复用唯一的多设备编排服务。停用独立直接写设备的旁路，避免多种修改入口维护不同的锁和状态。

**P2-08：管理端无法真正撤销快照查询权限**

位置：[auth.py:119](/root/ansible-firewalld-automation/api/auth.py:119)、[admin_ui.html:148](/root/ansible-firewalld-automation/api/static/admin_ui.html:148)。

**P2-09：CLI 提示符正则会把描述字段当成提示符**

位置：[run_usg_cli.py:15](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/files/run_usg_cli.py:15)、[run_usg_cli.py:87](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/files/run_usg_cli.py:87)。

`PROMPT_PATTERN` 在任何位置匹配尖括号或方括号文本，没有绑定设备身份和完整提示行。合法描述 `[maintenance]` 或 `<note>` 出现在命令回显/查询结果中时，会被当成命令完成。后续命令可能在上条响应尚未读完时发出，错误也可能被归给下一条命令。

复现：`description [maintenance]` 后面还有错误和真实 `[REAL-FW]` 提示符时，正则首先命中 `[maintenance]`。修复应在登录时识别设备提示格式，结合行边界和视图切换状态解析；用分片输出、命令回显、括号描述和延迟错误做伪终端测试。

**P2-10：缺少任务总截止时间，慢查询会占住全局锁及 API 执行资源**

位置：[runner_service.py:58](/root/ansible-firewalld-automation/api/runner_service.py:58)、[runner_service.py:211](/root/ansible-firewalld-automation/api/runner_service.py:211)、[worker.py:51](/root/ansible-firewalld-automation/api/worker.py:51)、[run_usg_cli.py:90](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/files/run_usg_cli.py:90)。

全局 flock 阻塞等待没有超时；Runner 没有设置 `timeout`/`job_timeout`、取消回调或总预算。当前安装的 ansible-runner 默认 `job_timeout`、`idle_timeout` 均为 None。CLI 每次分页/确认重新开始单次 timeout，持续输出可以不断延长执行。一个失控调用可阻塞全部父任务和全量查询。

全量查询又直接运行在同步 HTTP 请求内。并发请求可排队等同一把锁，占用有限的同步执行资源；客户端或反向代理超时并不会通过当前代码主动取消设备查询。前端按钮防重复不能限制其他客户端。

修复方向：为父任务、子调用、SSH 命令和锁等待分别设置受总截止时间约束的预算；取消时管理整个子进程组；对快照实行限并发、合并相同查询或短期缓存，繁忙时快速返回可重试状态。压测必须验证排队中的查询不会使健康、任务查询和提交接口一起失去响应。

**P2-11：基线预检可以无限重试，并长期阻塞后续同 IP 任务和普通快照**

位置：[worker.py:293](/root/ansible-firewalld-automation/api/worker.py:293)、[storage.py:443](/root/ansible-firewalld-automation/api/storage.py:443)、[main.py:461](/root/ansible-firewalld-automation/api/main.py:461)。

预检失败不增加子任务 attempt_count，也不应用 `firewall_child_max_attempts`；每次仍按固定间隔写入 `reconciling`。后续同 IP 的任务受旧任务阻挡，而普通快照遇到任意 reconciling 任务就拒绝。仓库没有取消或人工终止任务的 API。

复现：连续 5 次预检失败，计数仍为 0，状态一直 reconciling。临时失败可恢复，但永久错误不会自然进入终态。修复应为预检单独设置尝试/时间上限、退避和取消入口，并把“尚未修改设备的预检重试”与“已产生部分变更的修复中”区分。

**P2-12：没有账本且设备已漂移时，完整 deny 也无法执行**

位置：[worker.py:418](/root/ansible-firewalld-automation/api/worker.py:418)。

所有 action 都先要求多个设备的基线一致，之后才分支处理 `deny`。初次接管存在历史差异的设备、数据库恢复或丢失账本后，完整撤销本可使用固定目标“全部不存在”，当前却会因基线不一致失败。这限制了系统在故障处理中清理已有漂移的能力。

复现：A 有目标 IP/443，B 无目标 IP，无账本；提交 deny，任务失败，实际 mutation 调用数为 0。修复应为完整撤销采用明确的绝对期望状态，逐台验证对象归属并清理；保留对未知归属和解析异常的拒绝机制。

**P2-13：请求缺少幂等受理，超时重发可能在后续撤销之后重新放行**

位置：[jobs.py:41](/root/ansible-firewalld-automation/api/jobs.py:41)、[storage.py:270](/root/ansible-firewalld-automation/api/storage.py:270)。

相同 principal、相同 `client_request_id` 每次 POST 都产生新任务。文档明确将该字段定义为审计字段，因此这是已存在的设计限制，不是假定它承诺了去重。但对于生产调用，不能把设备增量动作的幂等性等同于请求受理的幂等性。

例如 allow 已入队但响应丢失，随后另一个操作者提交 deny，原调用方重试同一 allow，队列可成为 allow → deny → allow。最终执行会逆转后来的撤销意图。复现确认同请求号生成两个不同 job_id。

修复方向：提供以主体和幂等键为唯一约束的事务性受理；相同键/相同规范化请求返回原任务，相同键/不同请求返回冲突。为已有客户端明确迁移规则。

**P2-14：普通快照会轮转删除变更审计事件**

位置：[runner_service.py:222](/root/ansible-firewalld-automation/api/runner_service.py:222)、[runner_service.py:317](/root/ansible-firewalld-automation/api/runner_service.py:317)、[runner_service.py:789](/root/ansible-firewalld-automation/api/runner_service.py:789)。

同一台设备的快照与变更共用 artifact_root，均设置 `rotate_artifacts=20`。Runner 按该目录下全部运行轮转，查询次数足够多后，旧变更日志就被删除；数据库仍保留任务及 artifact 路径，事件接口对不存在目录返回空列表。一次业务任务本身也可能产生多个运行目录，保留 20 个运行不等于保留 20 个任务。

复现：在真实安装的 Runner 清理函数中建立一个旧变更目录和 20 个查询目录，旧变更目录被删除。修复应分离变更审计与查询缓存的保留策略，归档脱敏后的每次执行证据，并在审计过期时明确返回过期状态。

**P2-15：设备口令进入原始 Ansible 事件；敏感配置与普通 Git 配置共用文件**

位置：[access/main.yml:90](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/tasks/access/main.yml:90)、[snapshot/main.yml:55](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/tasks/snapshot/main.yml:55)、[resolve_firewall.yml:16](/root/ansible-firewalld-automation/roles/usg6000e_trade_access/tasks/resolve_firewall.yml:16)。

Role 将 `firewall_device` 和含密码的 `firewall_cli_environment` 存为 fact，相应任务没有 `no_log`。密码不在 CLI 参数中并不代表不会落盘，`suppress_env_files=True` 也不屏蔽事件中的 ansible_facts。

验证：使用纯本机 playbook 和虚构密码，Runner rc=0，至少一个事件 JSON 包含虚构密码。默认 artifact 目录权限为 0700，因此本次没有证明远程普通用户能经事件 API 读取口令；当前事件 API 也没有直接返回原始 res。本问题是日志、备份、调试包及本机读取面的密钥扩散。

当前工作区的 `group_vars/all.yml` 包含非占位口令且文件权限为 0600；它本身是已跟踪路径。本次检查 HEAD 版本只见占位值，没有证据声称真实口令已提交到 Git，也没有审计完整 Git 历史。

修复方向：敏感 fact 和包含秘密的执行任务设置 `no_log` 并验证真实事件脱敏；凭据移入 Vault/独立受保护配置或密钥服务。核对现有 artifacts 与备份的访问范围，再按实际泄露范围决定轮换。

**P2-16：健康检查无法发现 Worker 停滞或任务系统不可用**

位置：[main.py:115](/root/ansible-firewalld-automation/api/main.py:115)、[worker.py:73](/root/ansible-firewalld-automation/api/worker.py:73)。

`/healthz` 固定返回 ok，不检查数据库读写、Worker 心跳、最近消费进度和最老排队任务年龄。Worker 的 polling 异常会被循环捕获；它可以保持进程存活却持续无法工作。启动脚本检查子进程退出、systemd 自动重启可处理一部分故障，无法覆盖活着但不再推进的状态。

修复方向：保留轻量存活探针，增加就绪检查和 Worker 心跳/租约、队列延迟与执行超时指标。不要在每次健康检查中真实执行防火墙查询。验收应包含停 Worker、锁长期占用、数据库只读/磁盘耗尽和 Runner 卡住。

**P2-17：队列和变更临时目录没有容量边界与回收策略**

位置：[jobs.py:48](/root/ansible-firewalld-automation/api/jobs.py:48)、[runner_service.py:169](/root/ansible-firewalld-automation/api/runner_service.py:169)、[storage.py:270](/root/ansible-firewalld-automation/api/storage.py:270)。

受理没有全局或每主体的未完成任务上限；数据库任务、逐设备结果及每个变更的 local_tmp_dir 持续保留。快照临时目录有 TemporaryDirectory 回收，Runner artifacts 有轮转，但这些机制不清理变更目录，也不归档数据库任务。高频调用或长期运行会增加磁盘、查询和恢复成本，磁盘不足又会影响设备变更后的状态落库。

修复方向：限制队列深度和请求频率，超过容量明确返回可重试响应；按终态和保留期回收临时文件，归档任务及必要审计证据，监控磁盘与 WAL 增长。清理必须避开执行中任务，并与审计留存策略分开。

**P2-18：所有长期 API Key 共用一把刷新锁，慢请求会阻塞其他用户**

位置：[offline_api_keys.py:232](/root/ansible-firewalld-automation/api/offline_api_keys.py:232)、[offline_api_keys.py:345](/root/ansible-firewalld-automation/api/offline_api_keys.py:345)。

`authenticate()` 在同一个 service 全局锁内访问缓存、向 Keycloak 刷新、验证 JWT 并写回 Token。某个用户的慢刷新会使其他用户的 SK 请求等待，即便其他 key 的 access claims 仍在有效缓存中。

未来增加 API 进程时，这把 threading.Lock 又不能协调跨进程 refresh token 轮换。当前“失败后读最新 token 再试一次”有一定补救，但当另一个请求尚未写回、网络已完成刷新却写库失败或进程中断时，无法保证恢复。后半部分是带部署/轮换条件的风险，本次未用真实 Keycloak 验证 token 重用策略。

修复方向：按 key 合并刷新；让有效缓存读取避开无关 key 的网络锁；支持多进程时加入持久化刷新租约和版本校验，并验证轮换前后断网、写库失败和进程退出的恢复语义。扩大 API 进程数前先完成该验证。

**已具备、应保留的设计**

- API 默认启用认证；JWT 显式限制 RS256，并检查 issuer、audience 和必需时间/身份字段。
- 本地业务权限按稳定 sub 读取；普通任务读取检查归属，管理接口同时要求管理端 client、角色和本地权限。
- SQL 的业务值采用参数绑定；父任务及子任务创建使用事务，任务领取也有原子事务。
- 主 Worker 与全量查询共用父编排锁；设备执行独立加锁；每次 Runner 调用使用独立临时 env，避免 snapshot 变量污染后续变更。
- schema 对 IP、端口、description 控制字符、未知请求字段有明确校验；RFC1918 放行限制在多层执行链重复检查。
- 前端检查的主要动态结果使用 textContent/DOM 构造；本次没有确认可执行的前端注入或 shell 注入。
- 设备 busy、SSH 超时、引擎异步提交有局部处理；变更不是仅凭 Runner rc 判定，存在实时验证机制。

上述机制降低了正常路径及部分失败的风险，但不消除前述成功语义、原始状态可见性和恢复计划的缺口。

**需要明确的业务与运维边界**

- allowed_ips 当前不参与目标资源限制，最新业务文档明确取消了按管理员分配 IP 白名单限制；因此本报告没有将其当成遗漏的越权漏洞。若用户之间应隔离资产，需要重新定义资源归属规则。
- 完整跨设备原子事务并未实现。某台设备失败时，其他设备可能已变更；当前以有限重试加人工处理为边界。上线应接受并告警这种状态，而不能把“有重试”解释为原子性保证。
- `/check` 使用严格多数给人工建议，既不读取期望账本，也不证明多数设备的配置符合业务要求；共同漂移也可能被判一致。保持人工核实提示，处理 P1-02 后再用于完整漂移排查。
- 本地禁用会阻止后续请求，但已受理的排队任务没有执行前重新授权，也没有取消入口。需明确禁用是否应同时取消尚未下发的任务；如果需要，应加入受控取消和执行前检查。
- 浏览器 `oidc.js` 的 refresh 没有合并并发刷新；启用 refresh token 严格轮换时，应补充并发点击、页面初始化与刷新失败测试。这里没有将条件性掉登录扩大为已证明的身份绕过。
- 前端遇到一次轮询错误会停止自动跟踪；批量同步脚本的网络重试也需要总截止时间及可恢复批次状态。上线操作人员应能区分提交失败、提交结果未知和任务执行失败。

**建议的修复与验收顺序**

1. 先修 P1-01/02：定义并验证成功条件，确保未提交、未保存、部分虚拟系统残留均不能返回成功。
2. 修 P1-03/04：让恢复计划以任务完整期望状态为依据，所有删除先检查对象归属；处理中间端口重建失败时的恢复。
3. 修 P1-06，并统一所有生产写设备入口。未修 P1-07 的脚本应排除在生产操作流程之外；P3-05 的 SSH 加固不作为本次上线前置条件。
4. 加入截止时间、查询并发与队列上限、预检终止/取消、请求幂等、审计留存和 Worker 就绪检查。
5. 在与生产固件及拓扑一致的测试设备上进行故障演练，记录每台设备配置、引擎状态、保存结果及连续业务流量；通过后再进行小范围生产放量。

最小真机故障矩阵应包含：每个写入阶段 SSH 断开；commit 失败或超时；save 失败；多台中一台不可达；任意两个虚拟系统残留；Rule 删除旧端口后中断；应用同名但 IP 错配；Worker 在领取/落账本/下发/提交/落终态各阶段退出；人工改配置与恢复旧数据库；并发查询和重复提交；磁盘满；Keycloak 不可用及 Token 轮换。后续若启用 SSH 主机密钥校验，再补充主机密钥更换与轮换验收。

现有 178 项测试可作为回归基础，但大量设备行为由 mock 或静态字符串检查代替，不能证明 Huawei 实际视图切换、提交状态、保存成功和数据面连续性。当前阻塞点已有代码证据和本地复现，应先修复，再用该矩阵验证上线所需的恢复能力。
